# Mobile app classes (Android, iOS, cross-platform)

Built from OWASP MASVS v2 and MASTG/MASWE, Android's app-security risk documentation, RFC 8252, and published mobile deep-link and WebView research, reframed for diff-scoped source review.

## When to use

The diff adds or changes an app shipped to a phone: `AndroidManifest.xml`, `network_security_config.xml`, `backup_rules`/`data_extraction_rules`, `res/xml/*paths*.xml`, `build.gradle(.kts)`, `proguard-rules.pro`, `*.kt`/`*.java` that touch Activities, Services, Receivers, Providers, `WebView`, `Intent`, `Keystore` or `BiometricPrompt`; `Info.plist`, `*.entitlements`, `PrivacyInfo.xcprivacy`, `Podfile`/`Package.swift`, `*.swift`/`*.m`/`*.mm` that touch URL handlers, `WKWebView`, Keychain, `LAContext`, `URLSession` delegates or app extensions; or cross-platform code and config: `pubspec.yaml` and `lib/**/*.dart`, React Native (`package.json` with `react-native`/`expo`, `app.json`/`app.config.*`, native modules, `Linking`), `capacitor.config.*`, Cordova `config.xml`, Xamarin/.NET MAUI (`*.csproj` with `net*-android`/`net*-ios`). A mobile app is an untrusted client on a device shared with other apps; its server API belongs to `web-auth.md` and `data-isolation.md`, and a mobile CI or signing pipeline belongs to `supply-chain-ci.md`.

## Core discipline

```
- A mobile candidate needs an attacker-reachable entry and a named platform boundary. Entries: another app on the device (including a sideloaded or look-alike one), a link/QR/NFC/push/share-sheet payload, remote web content in a WebView, a network position, or a lower-trust server value. Boundaries: app sandbox, exported component, URL-scheme or link handler, WebView-to-native bridge, Keychain/Keystore, backup, or logs readable by others. Name both.
- A device owner, a rooted or jailbroken device, a debugger, or someone reversing the APK/IPA is not the attacker. Secrets and logic shipped in the binary are findings only when the secret grants server-side power or the logic is trusted server-side as a security decision; the client is always readable.
- Before assigning impact, state the declared minSdk/targetSdk or deployment target from the build files and apply that OS default. Android: `exported` defaults, cleartext default, `allowBackup`, WebView file access, PendingIntent mutability, App Links verification and `taskAffinity` behavior all change by API level. iOS: ATS default and Keychain class defaults. Do not assume an older or newer OS than the build declares.
- Count a mitigation only when it is visible in the repo on this path: explicit `exported=false`, `android:permission` with a signature-level protection, verified `autoVerify` plus a visible `assetlinks.json`/AASA, Network Security Config, `FLAG_IMMUTABLE`, an allowlisted-host check on a parsed URI, a Keychain accessibility class, a `CryptoObject`/`SecAccessControl` binding. An "expected" Play, App Store, MDM or OS control does not count.
- Use `needs_validation` for: server-hosted `assetlinks.json`/AASA content, store or MDM policy, push-provider payload shape, OS-version-dependent behavior outside the declared target, and signing or entitlement provisioning. State the exact check (file URL, command, setting).
- A bare weak setting with no reachable attacker input (debuggable in a debug-only variant, a cleartext exception for localhost, `allowBackup` on an app with no sensitive stored data) is a weakness note, not a finding.
```

## Android: component exposure and intents

- **Unintended export**: a new or edited `<activity>`/`<service>`/`<receiver>`/`<provider>` that is exported (explicit `exported="true"`, or an `intent-filter` present with a target SDK where that implies export) and performs a sensitive action, reads private data, or forwards an intent, with no `android:permission` and no in-code caller check. Check every sibling component in the same manifest, not only the changed one. Intent filters are not a security boundary; explicit-intent callers bypass them.
- **Intent redirection**: an exported component takes a nested `Intent`/`PendingIntent`/URI string from extras or data (`getParcelableExtra`, `Intent.parseUri`, `Intent.getIntent`, hand-rolled Parcel/Base64/JSON intent parsing) and calls `startActivity`/`startService`/`sendBroadcast`/`setResult`. Impact: launching non-exported components with the app's own identity, or reading private providers via forwarded `FLAG_GRANT_*_URI_PERMISSION`. Verify the target component and package are allowlisted after `resolveActivity`, flags and selector are cleared, or `IntentSanitizer` is used; `getCallingActivity()` being non-null is not a check.
- **`Intent.parseUri` in WebView or deep-link code**: `intent://` handled in `shouldOverrideUrlLoading` or from a link parameter and passed to `startActivity` with `URI_ALLOW_UNSAFE`, or with only the component cleared (the selector, the `BROWSABLE` category, or implicit matching of a non-exported activity can still be reachable).
- **URI grants and providers**: `grantUriPermissions="true"` plus forwarded external `Intent` data or flags; an exported provider whose `openFile`/`query` builds a path or SQL from the URI (`getLastPathSegment`, decoded segments, `..`, `%2F`) without a canonical-path check or parameterization; a `FileProvider` with `<root-path>`, `path="."`, or an `external-path` over sensitive data; a share target copying `EXTRA_STREAM` or a `content://`/`file://` result of `GET_CONTENT`/`PICK` into a readable location. Also an app trusting a provider-supplied `DISPLAY_NAME` as a local filename (overwrites app files), and zip extraction without canonical-path-contained entries.
- **PendingIntent**: created without `FLAG_IMMUTABLE` (or `FLAG_MUTABLE` with an empty or implicit base intent: no action, component, or package) and handed to another app, a notification, or an exported surface (the attacker fills in the intent and reaches non-exported components); or `FLAG_ONE_SHOT` missing on a once-only action. Auth decisions based on `PendingIntent.getCreator*()`/`getTarget*()` identify the creator, not the sender.
- **Implicit intents and broadcasts carrying secrets**: tokens, URLs with session data, or mutable objects in an implicit intent or an unprotected `sendBroadcast` (a look-alike app registers a matching filter); a dynamically registered or exported receiver acting on extras with no permission, `RECEIVER_NOT_EXPORTED`, or protected-broadcast filter; sticky broadcasts; `bindService` with an implicit intent.
- **Task hijack and tapjacking**: `allowTaskReparenting` or a custom `taskAffinity` on an auth-bearing activity with a low minSdk (Android's StrandHogg guidance ties the OS fix to API 30); a new confirmation or credential screen with no `filterTouchesWhenObscured` or overlay handling is a weakness note unless it gates a destructive or irreversible action.
- **Dynamic code loading**: `DexClassLoader`/`PathClassLoader`/`System.load` from external storage, a downloaded file, or another app's package with no signature or pinned-hash check.

## Android: WebView, links, storage and auth

- **Unsafe URI loading**: a deep link, intent extra, or push/notification field loaded via `loadUrl`/`evaluateJavascript` after a check that tests only the host, only the scheme, `startsWith`/`endsWith`/`contains` on the host string, or a regex; `javascript://`, `content://`, `file://`, `https://trusted@evil` and a lapsed or user-registrable allowlisted subdomain pass these. Impact is worst when the load adds auth headers or cookies (`loadUrl(url, authHeaders)`, `CookieManager.setCookie` for the URL) or exposes a bridge: a token goes to an attacker host, or script runs in an authenticated origin. Verify: parse with `Uri.parse`/`java.net.URI`, require `https` and exact host equality, and re-parse a `Uri` that arrived inside an `Intent`.
- **JS bridge exposure**: `addJavascriptInterface` (or `WebMessagePort`/`postWebMessage` with `*` origin) exposing tokens, files, intents, or actions to a WebView that can navigate to or render remote or user content. A bridge is reachable by every frame; treat any injected script as the caller. Static, APK-bundled content only is not a finding.
- **File access and chooser**: `setAllowFileAccessFromFileURLs(true)`/`setAllowUniversalAccessFromFileURLs(true)`, `setAllowFileAccess(true)` (the default is true at API 29 and below and false at 30+, per Android's documentation) with `setJavaScriptEnabled(true)` and attacker-influenceable URLs or HTML; `onShowFileChooser` results passed to the page unvalidated; unfiltered `content://` loads.
- **TLS error suppression in WebView**: `onReceivedSslError` calling `handler.proceed()`.
- **Deep-link verification and token carriage**: a new `VIEW`/`BROWSABLE` filter with a custom scheme, or `https` without `autoVerify`, that receives login, magic-link, reset, or OAuth values (another app registers the scheme and takes the code or token); links that auto-append the user's token to the opened URL. Treat the `assetlinks.json` content as `needs_validation` when it is not in the repo.
- **Storage**: tokens, keys, or PII in `SharedPreferences`, plain files, SQLite, or external storage; `android:allowBackup` true (or absent) with no `dataExtractionRules`/`fullBackupContent` exclusion for those files; `requestLegacyExternalStorage` or world-readable modes; secrets or PII in `Log.*` kept in release (no R8 strip rule visible); sensitive values placed on the clipboard; keys generated outside Android Keystore for data that must survive device theft.
- **Local auth**: a `BiometricPrompt` success callback used as a boolean gate with no `CryptoObject` and no Keystore key requiring user authentication (`setUserAuthenticationRequired(true)`, auth-per-use or short validity); `setInvalidatedByBiometricEnrollment(false)`; a `DEVICE_CREDENTIAL` or `BIOMETRIC_WEAK` fallback on a high-value action. A purely local biometric check that unlocks a server-issued secret already in plaintext storage protects nothing.
- **Cleartext and trust**: `usesCleartextTraffic="true"` or `cleartextTrafficPermitted="true"` in a base-config or non-localhost domain-config; `<certificates src="user"/>` trust anchors outside `debug-overrides`; `debug-overrides` or a trust-all `X509TrustManager`/`HostnameVerifier`/OkHttp `SSLSocketFactory` reachable in release builds (check the build type or flavor and for a `BuildConfig.DEBUG` guard); a removed or widened `pin-set`; `SSLSocket` without hostname verification.
- **Build config**: `debuggable true` in a release or shared build type; a release `signingConfig` or keystore password committed; `minSdk` lowered below a level the code relies on; API keys or secrets in `buildConfigField`/`strings.xml`/`gradle.properties` (secret-bearing, not a key restricted to package and signing certificate).

## iOS

- **Custom URL scheme and Universal Link handlers**: `application(_:open:options:)`, `onOpenURL`, `scene(_:openURLContexts:)`, or `continue userActivity` acting on host, path, or query without an allowlist, or on `sourceApplication` as trust. Custom schemes are not unique to one app, so tokens, OAuth codes, or magic links delivered through them are interceptable; a handler that navigates, logs in, links an account, or loads a URL from a parameter is an entry for any web page or app. A new `applinks:` entry or AASA claim that is not verified in the repo is `needs_validation`.
- **ATS**: `NSAllowsArbitraryLoads` true, `NSAllowsArbitraryLoadsInWebContent`, or `NSExceptionDomains` with insecure HTTP, a lowered TLS minimum, or `NSIncludesSubdomains` on a domain handling credentials or tokens; third-party exception keys covering an SDK. A `localhost` or `NSAllowsLocalNetworking` exception is a weakness note.
- **Trust bypass**: a `URLSessionDelegate` `urlSession(_:didReceive:completionHandler:)` or `WKNavigationDelegate` `didReceive challenge` returning `.useCredential` with `URLCredential(trust:)` and no `SecTrustEvaluate` or pin comparison; Alamofire/AFNetworking trust evaluation disabled; `allowInvalidCertificates`/`validatesDomainName = false`.
- **Keychain and data protection**: `kSecAttrAccessibleAlways*` (deprecated), or a long-lived token or key with `AfterFirstUnlock` where `WhenUnlockedThisDeviceOnly`/`WhenPasscodeSetThisDeviceOnly` is needed; `kSecAttrSynchronizable` true on device-bound secrets; secrets in `UserDefaults`, plist, Core Data, or files with `.noFileProtection`; sensitive files not marked `isExcludedFromBackup`; Keychain items left in a shared access group or app group readable by other apps or extensions of the same team.
- **Local auth**: an `LAContext.evaluatePolicy` result used as a boolean gate with no Keychain item protected by `SecAccessControl` (`.biometryCurrentSet`, `.userPresence`) and `kSecUseAuthenticationContext`; a `deviceOwnerAuthentication` fallback on a high-value action.
- **WKWebView**: `WKScriptMessageHandler`/`WKScriptMessageHandlerWithReply` exposing native actions to a view that loads remote or user content, with no `message.frameInfo.securityOrigin`/`isMainFrame` check; `evaluateJavaScript` built by string interpolation of link or message data; file-URL access widened (`allowFileAccessFromFileURLs` and `allowUniversalAccessFromFileURLs` are set through private KVC keys) or `loadFileURL` with a broad `allowingReadAccessTo`; `javaScriptEnabled`/`WKPreferences` widened; deprecated `UIWebView`.
- **Entitlements and extensions**: new `*.entitlements` keys (`com.apple.security.application-groups`, `keychain-access-groups`, associated domains, `get-task-allow` true in release, `aps-environment`, HealthKit or background modes) with no matching feature; app extensions or share and pasteboard use (`UIPasteboard.general` writes of secrets without `.localOnly` or an expiry); sensitive screens with no snapshot cover in `applicationWillResignActive`; secrets, tokens, or PII passed to `NSLog`/`print`/`os_log` without `.private`.
- **Info.plist**: `LSApplicationQueriesSchemes`, `UIFileSharingEnabled`/`LSSupportsOpeningDocumentsInPlace` exposing the Documents directory, `NSAppTransportSecurity` (above), generic `CFBundleURLTypes` scheme names, or new usage-description keys added for a permission with no clear user-facing use (a privacy note only).

## Cross-platform and hybrid

- **React Native**: tokens, refresh tokens, or keys in `AsyncStorage`/`MMKV`/Redux-persist (use Keychain/Keystore-backed storage such as `react-native-keychain` or `expo-secure-store`); secrets or API keys in `.env`/`react-native-config`/`app.json` `extra` (they ship in the bundle); `Linking.getInitialURL`/`addEventListener('url')` or navigation `linking.config` that routes to a screen or action from untrusted params, or sends tokens through the scheme; `react-native-webview` with `originWhitelist={['*']}`, `javaScriptEnabled`, `onMessage` driving native modules, `injectedJavaScript` built from strings, `allowFileAccess`/`allowUniversalAccessFromFileURLs`; native modules or TurboModules that accept JS-supplied paths, URLs, or intents and perform file, process, or intent actions; OTA updates (CodePush, Expo/EAS Updates, custom) pointed at a URL or channel without code signing (`updates.codeSigningCertificate` not configured) or with rollout controlled by a lower-trust party.
- **Flutter/Dart**: `HttpClient.badCertificateCallback = (_, __, ___) => true`, an `IOClient` built on it, a `SecurityContext` that trusts everything, or `dio` `onHttpClientCreate` doing the same, in non-test code; secrets in `SharedPreferences`/Hive unencrypted rather than `flutter_secure_storage` (check its Android and iOS options for accessibility class and backup); `MethodChannel`/`EventChannel` handlers (Kotlin/Swift) that take Dart-supplied paths, URLs, or intents without validation and are invoked from a WebView plugin; `webview_flutter`/`flutter_inappwebview` JS channels and `shouldOverrideUrlLoading` with the same checks as native WebViews; `go_router`/`onGenerateRoute` deep-link routing to privileged screens without an auth gate.
- **Capacitor/Cordova/Ionic**: `server.url` or `server.cleartext` in a non-development config, `server.allowNavigation: ['*']` or broad domains; Cordova `<access origin="*">`, `<allow-navigation href="*">`, `<allow-intent href="*">`/`intent:`/`market:`; CSP absent or `unsafe-inline`/`unsafe-eval`/`*`; remote or user HTML rendered in the same WebView as plugins (every plugin becomes callable by that script; `innerHTML` of server content); new community plugins that expose files, shell, intents, or secure storage; `Preferences` used for tokens; deep-link `appUrlOpen` handlers that `router.navigate`/`window.location` from URL params. Verify these option names against the pinned Capacitor or Cordova version.
- **Xamarin/.NET MAUI**: `ServicePointManager.ServerCertificateValidationCallback` or `HttpClientHandler.ServerCertificateCustomValidationCallback` returning true; `Preferences` used for secrets instead of `SecureStorage` (which on Android sits in backup-eligible preferences unless excluded, per Microsoft's documentation); a `WebView` with JS and `Navigating` handlers that call `EvaluateJavaScriptAsync` from URL data; Android and iOS platform folders inherit every native class above.
- **SDK and dependency additions**: a new analytics, ads, crash, push, deep-link, or auth SDK that receives tokens or PII or registers its own exported components or URL schemes (inspect the merged-manifest effect and the entitlements it adds in the diff); a package pulled from a non-standard repository, branch, or local path; library bumps that remove a pin or change TLS defaults. Version and known-CVE questions belong to `supply-chain-ci.md`.

## Validation rules

```
1. Name the attacker entry (other app, link/QR/push/share payload, remote web content, network position, lower-trust server value), the crossed boundary, the intended control, the affected user or data, and the concrete result (token captured, private file read, component launched with app identity, action performed).
2. State the declared minSdk/targetSdk or iOS deployment target and the OS default that applies. Cite the visible control on the path (exported flag, permission, host check, Network Security Config, ATS, Keychain class, CryptoObject binding) and say why it does not stop the attack. If another visible layer stops it, it is hardening, not a finding.
3. For intent, URL, and bridge claims, trace the value from entry (extra, data, link parameter, message) to the sink (startActivity, loadUrl, evaluateJavaScript, openFile, token header) through every check; show the check fails for the payload (scheme, host, selector, encoding), not merely that it is imperfect.
4. For WebView and bridge claims, show what remote or user-controlled content can load into that WebView and what the bridge or loaded origin can reach.
5. For storage, logging, backup, and local-auth claims, show a reader that is not the device owner (another app, a backup, a log reader with a permission, a later user) and that the data is secret-bearing; a boolean-only biometric result is a finding only when the guarded action or secret is attacker-reachable without it.
6. Server-hosted or store/OS facts (assetlinks.json/AASA, pinning certificates, MDM, push payload shape, entitlement provisioning) are `needs_validation` with the exact check. A secret is a finding only if it grants server-side power; show the capability, not the string.
7. Debug or test-only config counts only if it reaches a release build (build type, flavor, or a missing guard is shown). A bare weak default with no reachable input is a weakness note.
8. Show the change introduced or exposed it.
```
